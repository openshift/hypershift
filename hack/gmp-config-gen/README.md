# gmp-config-gen

Generates the Google Managed Prometheus (GMP) `PodMonitoring` manifests from the
CoreOS `ServiceMonitor` / `PodMonitor` definitions. The CoreOS monitors remain
the source of truth; do not hand-edit a generated file, change its source and
regenerate:

```bash
make generate-gmp-config   # rewrite the generated files
make verify-gmp-config     # fail if they are stale
```

CI runs `verify-gmp-config` as part of `make lint`.

Every output is named `gmp-podmonitoring.yaml` and starts with a
`# Code generated by hack/gmp-config-gen; DO NOT EDIT.` header. It lives next to
its source, in one of two places:

| Kind | Source | Output |
| --- | --- | --- |
| Component monitor | `servicemonitor.yaml` / `podmonitor.yaml` in `control-plane-operator/controllers/hostedcontrolplane/v2/assets/<component>/` | `v2/assets/<component>/gmp-podmonitoring.yaml` |
| Management monitor (`operator`, `external-dns`) | Go constructors in `cmd/install/assets/hypershift_operator.go` | `cmd/install/assets/gmpmonitoring/<name>/gmp-podmonitoring.yaml` |

Management monitors have no component directory, because `hypershift install`
builds them in Go. Their manifests carry a namespace placeholder, since the
install namespace is configurable.

Components that can never run on a GMP platform get no file. They are listed with
a reason in `metrics.GMPUnsupportedComponents` (`support/metrics/gmp_monitoring.go`),
today `karpenter` and `karpenter-operator`, because Karpenter runs only on AWS and
Azure. The generator stages nothing for them and removes a file it generated
earlier. Add a component there only if it can never run on a platform that uses
GMP; a component the generator merely cannot represent yet is excluded in
`main.go` instead, with a parity waiver.

## Changing a CoreOS monitor

When a CoreOS `ServiceMonitor` or `PodMonitor` changes, run `make generate-gmp-config`
and commit the result. `make verify-gmp-config` (in `make lint`) and the parity test
in `test/parity/gmpmonitoring` (in `make test`) both fail until you do.

The generator fails, instead of dropping a setting, when it cannot represent one in
GMP, for example `honorLabels`, `bearerTokenSecret` or `authorization`. In that case:

1. Remove the setting if the CoreOS monitor does not need it.
2. Otherwise ask the GCP HCP team to extend the generator.
3. To merge before that lands, add the component to `excludedComponents` in
   `main.go` and waive its scrape target in
   `test/parity/gmpmonitoring/waivers.yaml`. A waiver needs a tracking issue and a
   reason, and the test fails once the waiver is stale.

If the parity test reports an uncovered target after you regenerated, the
generator represents the monitor wrongly. That is a generator bug, so waive the
target the same way and tell the GCP HCP team.

## Why the generated files are inert

Nothing reads a generated file at runtime yet.

- **Component files** are in `v2/assets`, which the component framework
  (`support/controlplane-component`) walks with `assets.ForEachManifest`, applying,
  deleting and reporting everything it yields. That walk **skips every file whose
  name starts with `gmp-`**, so no HostedControlPlane applies a GMP manifest, on
  any platform.
- **Management files** are not embedded, and `hypershift install` does not read
  them.

`TestGMPManifestsAreNotWalked` keeps the prefix honest:

- a file that declares a GMP resource (a `PodMonitoring` kind or a
  `monitoring.googleapis.com` apiVersion) must carry the `gmp-` prefix, so a GMP
  monitor cannot be added under a name the walk would apply;
- a `gmp-` file must declare a GMP resource, so the skip cannot silently hide a
  CoreOS manifest;
- `ForEachManifest` must yield no `gmp-` file for any component.

The follow-up that activates GMP monitoring opts in to these files, for GCP only,
behind the management-cluster flag and the control-plane-operator image label.

## Labels

Series labels follow what Prometheus on the management cluster produces for the
CoreOS monitors (`job` is the Service name, `endpoint` the port name), so
dashboards and alerts give the same result for CoreOS and GMP control planes on
one management cluster. The `hypershift.openshift.io/metrics-*` annotations on
the CoreOS monitors configure `metrics-proxy` forwarding into the hosted
cluster, a separate path that is only active when metrics forwarding is
enabled. GMP never reads them, so the generator does not copy them.
